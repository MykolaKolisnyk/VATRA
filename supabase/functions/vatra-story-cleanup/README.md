# VATRA — очищення історій через 24 години

Історія зберігається в `public.app_data` як `posts/<id>` із `kind: "story"`.
Клієнт показує її не довше 24 годин. Якщо автор знову відкриє стрічку,
клієнт видаляє свої прострочені записи та їхні файли.

## Серверне очищення

Edge Function `vatra-story-cleanup` уже розгорнуто у проєкті VATRA. Вона
доступна **лише** зі службовим ключем у заголовку `apikey`. Вона видаляє
медіа через Storage API, а потім записи у базі. Працює зі старими історіями
у `vatra-media` і новими у приватному `vatra-stories`.

У production вже ввімкнено `pg_cron` та `pg_net`, а також створено завдання
`vatra-story-cleanup-every-15m`, яке викликає Edge Function кожні 15 хвилин.
**Завдання нічого не відправлятиме, доки не створений Vault-secret**.

Для активації: Supabase → Settings → API Keys → створити окремий secret key
для фонового очищення; не зберігати його у фронтенді чи GitHub.
Supabase SQL Editor (лише приватна адміністративна сесія):

```sql
select vault.create_secret('ВСТАВИТИ_СЛУЖБОВИЙ_SECRET_KEY',
                          'vatra_story_cleanup_secret');
```

Не надсилайте ключ у чат. Перевірити стан завдання можна SQL-запитом:

```sql
select jobid, jobname, schedule, active
from cron.job where jobname='vatra-story-cleanup-every-15m';
```

Можна протестувати функцію з `{"dryRun":true}` через секретну службову
авторизацію. Відповідь `expired` показує кількість прострочених історій,
`deleted` — кількість видалених.

Для приватності нових історій використовується `vatra-stories` (private)
та `createSignedUrl` з п'ятихвилинним терміном дії; доступ перевіряє
Storage RLS через актуальний запис історії, її аудиторію, автора та строк дії.
SQL-політики у `supabase/setup-vatra-stories-private.sql`.

**Сумісність:** старі записи (якщо вони з'являться з попередньої версії) з публічними URL не стають приватними автоматично. Нові історії завантажуються лише в приватний бакет. Сховище `vatra-media` має залишатися публічним для звичайних фотографій і відео.
