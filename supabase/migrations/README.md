# Міграції бази даних VATRA

Ця папка зберігає **версійні SQL-міграції PostgreSQL для Supabase**: структуру таблиць, індекси, RLS-політики, права доступу, функції та тригери. Це не CSS/JS і не частина браузерного інтерфейсу.

> **Увага · історія неповна.** Перевірка 12 листопада 2026 року показала: у віддаленому проєкті VATRA зареєстровано **51 міграцію**, а в цій папці — лише **11 останніх**. Попередні 40 файлів тут відсутні. Не вважайте папку повною схемою для відновлення або повторного створення бази. Для повної відтворюваності потрібно окремо відновити перевірені історичні SQL-файли або створити й перевірити повний початковий стан схеми. **Не виконуйте `supabase db reset` на основі цієї неповної історії, очікуючи відтворення поточної бази.**

## Як читати назви

Формат Supabase: `РРРРММДДГГХХСС_короткий_опис.sql`.

Наприклад, `20261111142326_profile_status_presence.sql` означає версію **2026-11-11 14:23:26**, а решта назви підказує, яку функцію змінено. Числова частина потрібна для історії застосування: **не перейменовуйте, не видаляйте й не об’єднуйте вже застосовані міграції**. Дрібні файли з `grant` або виправленням RLS — це окремі наступні зміни, а не дублікати.

## Правила для подальшої розробки

1. **Не змінювати історичні SQL-файли**, уже застосовані до робочої бази. Виправлення виконувати новою міграцією після аналізу залежностей.
2. **Нові файли створювати через Supabase CLI** (`supabase migration new <опис>`): CLI присвоює коректний часовий префікс. Писати короткі, читабельні назви англійською у `snake_case`, наприклад `add_profile_city_index`.
3. **Не плутати GitHub і Supabase**: коміт SQL у репозиторій не доводить, що його застосовано в базі. Порівнювати локальну та віддалену історію командою `supabase migration list --remote` або через Supabase Dashboard.
4. **Не запускати SQL повторно навмання.** Особливо обережно зі змінами `RLS`, `GRANT`, `SECURITY DEFINER`, `DROP`, тригерами й міграціями з оновленням даних.
5. Зміни бази тестувати спочатку на **ізольованій тестовій базі**; перед змінами робочої бази — мати перевірений план відновлення.
