# ВАТРА — доставка кодів авторизації

Код застосунку вже використовує `supabase.auth.signInWithOtp` та `verifyOtp` через `vatra-backend.js`, без зберігання секретних кодів у браузері чи у власній SQL-таблиці. Ці шаблони є вихідними файлами конфігурації — **GitHub Pages не застосовує їх до Supabase автоматично**.

## Міжнародний брендинг та мова листів

**VATRA відкрита для користувачів з будь-якої країни.** У листах немає гасла «для своїх» чи твердження, що сервіс лише для українців. Ім'я відправника — `VATRA`. Тема листа за замовчуванням нейтральна (`VATRA — Verification code`).

Шаблон `otp-email.html` містить переклади українською, англійською, польською, німецькою, французькою, іспанською, португальською та італійською. При **новій реєстрації** клієнт зберігає обрану мову сайту в `auth.users.raw_user_meta_data.preferredLanguage` через параметр `options.data` у Supabase OTP. Шаблон відображає мову через безпечні умовні конструкції `{{ if eq .Data.preferredLanguage "uk" }}` тощо. Для інших кодів мови — англійська. Це стосується лише email; для SMS поки є короткий нейтральний англомовний текст, бо стандартний SMS-шаблон не гарантує доступу до мовних уподобань одержувача.

**Після оновлення файлу в GitHub потрібно повторно скопіювати HTML у Supabase → Authentication → Emails → Templates** для трьох типів: Confirm sign up, Magic link or OTP, Reset password. GitHub не синхронізує шаблони Supabase автоматично. Для поточної живої (ще не оновленої) сторінки відновлення пароля також потрібне посилання `{{ .ConfirmationURL }}` у шаблоні Reset password; не видаляйте його, доки не розгорнуто й перевірено OTP-відновлення. Відсутність валідних Gmail SMTP-даних помилки `535 5.7.8` оновленням HTML не усуває. Перевірте відправника окремо.

**База акаунтів не очищається цією зміною.** Користувач сам вирішує, чи потрібне очищення тестових акаунтів, окремо від оновлення листів.


## Поточний етап: лише GitHub Pages, власного домену немає

Публічна адреса ВАТРИ лишається `https://mykolakolisnyk.github.io/VATRA/`. Для авторизації через код не потрібно переносити сайт на інший хостинг. Але домен `github.io` належить GitHub: **не можна** відправляти листи від `noreply@github.io` чи підтвердити його DNS для Resend.

**Тимчасовий тестовий варіант без покупки домену:** створіть окрему поштову скриньку Gmail для ВАТРИ. Увімкніть двоетапну перевірку і створіть пароль застосунку, якщо він доступний для цього акаунта. Використовуйте адресу скриньки як `VATRA_EMAIL_FROM` та `VATRA_SMTP_USER`, адресу сервера `smtp.gmail.com`, порт `587` (або `465`), а пароль застосунку — як `VATRA_SMTP_PASSWORD`. Ім'я відправника в листі буде **ВАТРА**, але реальна адреса лишиться `...@gmail.com`. Gmail — тільки пілот із малими обсягами, не рекомендований для масової реєстрації. Не використовуйте основний пароль Google. Шаблон — `delivery.env.example`.

Канали можна налаштовувати **незалежно**: `VATRA_AUTH_CHANNEL=email` вмикає налаштування лише пошти й не змінює SMS-параметри; `sms` — лише SMS, `both` — обидва. Таким чином відсутність Twilio не блокує налаштування Gmail. Це не запускає OTP у браузері автоматично: до живого розгортання PR треба перевірити доставку.

**Для публічного запуску** рекомендовано придбати або іншим законним способом отримати контроль над поштовим доменом, налаштувати SPF/DKIM/DMARC та SMTP (Resend/Postmark/інший). Сайт при цьому може залишитися на GitHub Pages. SMS окремо потребує договору з провайдером, оплати за повідомлення та, за потреби, узгодження Sender ID `VATRA`.

## Автоматичне налаштування через Management API

Скрипт `tools/configure-vatra-auth.mjs` автоматизує налаштування брендованих email-шаблонів та SMS-провайдера у Supabase. Він використовує **офіційний** endpoint `PATCH /v1/projects/rjasunoawrxvetwadylh/config/auth`, а не зміни у SQL-таблицях. Виконати його можна з комп'ютера адміністратора, де змінні середовища доступні лише цьому процесу.

1. Для пілотного тесту використати окрему адресу Gmail і пароль застосунку; для публічного запуску підключити власний підтверджений поштовий домен до SMTP-провайдера (Resend, Postmark тощо). Отримати справжню адресу/логін/пароль.
2. Для SMS окремо зареєструвати власний акаунт у Twilio, Vonage або MessageBird, перевірити доставку до потрібних країн і підтвердити Sender ID `VATRA`, якщо підтримується. Якщо SMS-провайдера поки немає, встановити `VATRA_AUTH_CHANNEL=email`.
3. Створити Supabase Management API token з правом `auth_config_write`, заповнити змінні із `delivery.env.example` **лише в приватному оточенні**. Не додавати ці значення у репозиторій чи повідомлення.
4. Запустити `node tools/configure-vatra-auth.mjs --dry-run`: скрипт перевірить обов'язкові поля, але не надішле запити й не змінить Supabase. Далі `node tools/configure-vatra-auth.mjs --apply`, щоб записати конфігурацію.
5. Перевірити у Supabase Authentication → URL Configuration, що дозволено `https://mykolakolisnyk.github.io/VATRA/auth.html?mode=new-password`. Скрипт не перезаписує наявний список redirect URLs, щоб не пошкодити інші інтеграції.
6. Перевірити реальне отримання одного OTP-листа та одного SMS на власні контрольовані контакти, потім входження `verifyOtp`. Окремо перевірити ім'я реального SMS-відправника у телефоні: текст `ВАТРА` всередині повідомлення **не гарантує** Sender ID.
7. Налаштувати серверні rate limits, CAPTCHA та обмеження за країнами, перевірити журнали провайдерів. Лише після цього об'єднувати OTP-only реєстрацію в робочу `main`.

Налаштування SMTP/SMS і тестові SMS можуть потребувати оплати або підтвердження власника відповідних облікових записів. GitHub/Supabase конектор сам по собі не має доступу до зовнішніх сервісів і секретів. **Не створюйте фальшиві OTP або «успішні» відповіді без справжньої доставки.**

## Пошта — обов'язкові налаштування адміністратора

1. Для пілота без власного домену можна використати окрему Gmail-адресу з SMTP; для публічного запуску перевірити свій поштовий домен у SMTP-провайдері.
2. У Supabase → Authentication → SMTP Settings налаштувати SMTP host, порт, логін, пароль і дійсну адресу відправника (для Gmail вона має збігатися з SMTP-користувачем), **Sender name: ВАТРА**. Паролі та API-ключі не зберігати у репозиторії.
3. У Authentication → Email Templates вставити міжнародний шаблон `otp-email.html` для **Confirm signup**, **Magic link / OTP** та **Reset password**. У всіх має залишитися `{{ .Token }}`. Теми: `VATRA — Verify your email`, `VATRA — Verification code`, `VATRA — Reset your password`. Для старої живої сторінки відновлення залиште також `{{ .ConfirmationURL }}`.
4. Перевірити Authentication → Providers → Email, Site URL та дозволені redirect URLs для `https://mykolakolisnyk.github.io/VATRA/auth.html`, включно з `?mode=new-password`.
5. Зробити тест на **власну** контрольовану пошту. Не тестувати масовою відправкою.

Без власного SMTP штатний Supabase обмежує листи тестовими адресами організації; реєстрація сторонніх користувачів через email не буде надійно доступна.

## SMS — обов'язкові налаштування адміністратора

1. Створити та підключити обліковий запис SMS-провайдера, який підтримується Supabase Auth (наприклад, Twilio, Vonage, MessageBird), із дозволеним надсиланням в Україну.
2. Authentication → Providers → Phone: увімкнути Phone, налаштувати SMS credentials і дозволені країни, вимагати підтвердження номера.
3. Authentication → SMS Templates: вставити текст `otp-sms.txt`, де код підставляється як `{{ .Code }}`.
4. Для імені відправника **VATRA** потрібна підтримка буквено-цифрового Sender ID цим оператором у відповідній країні та, за необхідності, реєстрація назви. Назва в тексті SMS сама по собі **не змінює** відправника.
5. Запустити один тест на власний номер у міжнародному форматі `+380XXXXXXXXX` і перевірити журнали провайдера.

## Захист та сумісність

- Діє обмеження повторного надсилання в інтерфейсі на 60 секунд; серверні rate limits і CAPTCHA необхідно також налаштувати в Supabase.
- Паролі існуючих акаунтів збережені: доступний вхід із паролем як резервний спосіб.
- Коди перевіряє Supabase, а не клієнтський JavaScript; без відповіді Auth-провайдера сторінка не підтверджується.
- Секрети SMTP/SMS, провайдерські акаунти та тарифи не можуть бути створені лише через файли GitHub. Поки їх не підключено, ніхто не повинен обіцяти фактичну доставку повідомлень.
