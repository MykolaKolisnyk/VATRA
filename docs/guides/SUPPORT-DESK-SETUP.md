# ВАТРА — встановлення системи техпідтримки

Потрібні **всі попередні міграції** (база, унікальні @псевдоніми, модерація, штатні ролі) та **нова**:

**`VATRA/vatra-support-desk.sql`**

Відкрийте Supabase → SQL Editor і виконайте файл після `vatra-staff-verification.sql`. Виконувати власником бази даних, не з браузера користувача. Файл не видаляє існуючі дані. SQL працює в одній транзакції `begin / commit`.

## Як працює

- **Будь-який авторизований користувач:** меню аватара → **«Техпідтримка ВАТРИ»**, або Налаштування → **«Зв’язатися з техпідтримкою»**. Створює звернення (тема та текст) та може спілкуватися в його захищеному діалозі.
- **Техпідтримка:** отримує автоматично призначені звернення у своїй черзі. Алгоритм обирає працівника зі статусом `support` та найменшою кількістю незакритих звернень. Якщо працівників немає, звернення лишається непризначеним. Техпідтримка може прийняти таке звернення.
- **Власник:** Адмінпанель → **«Техпідтримка»**, переглядає всі офіційні розмови, може відповісти та перепризначити відповідального працівника через UID. Інші адміністратори та модератори не отримують автоматичного права читати ці розмови.
- **Живий чат:** під час відкритої сторінки є автоматичне оновлення приблизно кожні 9 секунд. Це не фонове push-сповіщення й не WebSocket.
- **Статуси:** нове, в роботі, вирішене, закрите.
- **Журнал власника:** записуються відповіді працівників (із текстом), відкриття службових звернень, призначення та зміни статусів. Власник може переглядати інші службові дії персоналу через загальний аудит. Повідомлення підтримки та журнал — різні таблиці.

## Захист даних

- Розмову може читати її автор, призначений співробітник техпідтримки та власник ВАТРИ. Спеціалісти техпідтримки бачать також *непризначені* заявки, але їхній текст — лише після прийняття.
- Користувачі не можуть безпосередньо вставляти/редагувати повідомлення в таблицях через REST. Для запису використовуються серверні RPC з авторизацією.
- Власник переглядає повний журнал персоналу. Рядки службового аудиту доступні лише власнику після цієї міграції, оскільки можуть містити текст службових відповідей.
- **Особисті розмови користувачів** у месенджері не відкриваються власнику або техпідтримці через цей модуль.
- Звернення може бути закрите відповідальним працівником або самим користувачем (користувач може лише закривати власне звернення).

## Посадові інструкції

Файл [STAFF-RULES.md](./STAFF-RULES.md) визначає обов’язки та заборони власника, адміністратора, модератора, техпідтримки і верифікатора. Кожен співробітник бачить інструкцію своєї ролі у вкладці «Обов’язки» адмінпанелі.

## Перевірка після встановлення

1. Переконайтесь, що власник зареєстрований у `vatra_network_owners`, а тестовий співробітник має роль `support` у `vatra_staff_members`.
2. Увійдіть іншим тестовим акаунтом, створіть звернення.
3. У працівника техпідтримки перевірте появу нового звернення та відповідь. У користувача — автоматичне отримання відповіді, поки сторінка підтримки відкрита.
4. У власника перевірте перегляд усіх звернень, перепризначення за UID та журнал.
5. Спробуйте отримати чужі повідомлення прямим REST-запитом із токеном іншого користувача — доступ має бути заборонений.
6. Перевірте, що роль `moderator` і `verifier` не може переглянути чужі звернення чи повний аудит.
7. Зніміть у тестового працівника роль `support`, оновіть сесію й переконайтесь, що доступ припинено.

**GitHub-оновлення саме по собі не встановлює SQL у живий Supabase.** Власник повинен виконати міграцію та перевірити поведінку на тестових акаунтах.
