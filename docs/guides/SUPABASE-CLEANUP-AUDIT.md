# ВАТРА: аудит таблиць Supabase без видалення даних

Дата перевірки коду: 31 жовтня 2026.

## Виявлено в репозиторії

Основний браузерний модуль `vatra-backend.js` використовує `const TABLE = 'app_data'` і виконує читання/запис через `client.from(TABLE)`. Дані профілів, дописів, дружби, коментарів і спільнот лежать у `app_data` як JSONB зі шляхами на кшталт `publicProfiles/UID`, `posts/ID`, `friends/UID`, `groups/ID`. Це **не** означає, що інші таблиці гарантовано порожні або ніколи не використовувалися.

Репозиторій містить спеціалізовані SQL-таблиці, які не можна вважати зайвими без перевірки:
- `vatra_moderation_*`: блокування користувачів/спільнот, скарги, журнал, прихований контент
- `vatra_support_*`: заявки до підтримки, повідомлення та сповіщення
- `vatra_staff_members`, `vatra_network_owners`, `vatra_verification_*`: права персоналу й перевірка
- `vatra_account_lifecycle`, `vatra_account_tombstones`: запити на видалення, статус видалення
- `vatra_scheduled_posts`, `vatra_otp_codes`: планування дописів, одноразові коди

У репозиторії **не знайдено звернень основного браузерного адаптера** до однотипних окремих таблиць `profiles`, `private_profiles`, `posts`, `post_comments`, `post_likes`, `messages`, `conversations`, `friendships`, `saved_posts`, `communities`, `community_members`. Це кандидати на **подальше** обстеження, не список для видалення. Вони можуть використовуватися іншими сервісами, SQL-функціями, сторонніми клієнтами або зберігати старі дані.

## Що саме створювало навантаження

`vatra-backend.js` раніше підписувався на Realtime для `app_data` і **додатково** опитував кожну підписку через SQL-запит що 20 секунд, навіть на прихованій вкладці. `script.js` створює багато підписок на цілі набори даних, зокрема `posts`, `comments`, `publicProfiles`, `groupPosts`.

Поточна оптимізація: для більшості таких підписок запасна перевірка кожні 60 секунд; для чатів, запитів дружби й індексів розмов — 20 секунд; у неактивній вкладці регулярне опитування пропускається, а при поверненні виконується оновлення. Realtime залишається ввімкненим. Якщо Realtime не працює, новини можуть оновитися із затримкою до 60 секунд.

## Перед будь-яким очищенням

1. Запустити **`VATRA/supabase-read-only-audit.sql`** — це лише SELECT, жодних DROP/DELETE/UPDATE.
2. Перевірити розмір, приблизну кількість рядків, лічильники читання/запису, RLS і зовнішні ключі. Лічильники PostgreSQL з моменту скидання статистики; їх нуль не доводить непотрібність таблиці.
3. Знайти залежності в SQL-функціях, тригерах, Edge Functions, cron, Storage та інших зовнішніх клієнтах. Для таблиць, які здаються застарілими, створити резервну копію й план відновлення.
4. Лише після перевірки **в тестовому проєкті** вирішити, що можна архівувати або видаляти. Не виконувати DROP у production наосліп.

## Організація Supabase

Таблиці в `public` відображаються одним переліком у Supabase Table Editor — це нормальна організація PostgreSQL, а не доказ, що вони разом завантажуються. Для майбутньої архітектури можна розділити підсистеми на SQL-схеми (`core`, `social`, `moderation`, `support`), але **просте переміщення існуючих таблиць порушить поточні SQL-функції, RLS і API-клієнт**. Спочатку потрібні узгоджені міграції й перевірки.

Наразі першочергове: відновити інтерфейс після помилки `$('a[data-page]').forEach`; потім виміряти навантаження, а не чистити таблиці за назвою.
