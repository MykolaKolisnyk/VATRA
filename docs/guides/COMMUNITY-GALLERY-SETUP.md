# ВАТРА — права публікації, фото/відео спільнот і коментарі

Усі дані в Supabase. GitHub Pages не може застосувати SQL автоматично, тому ці міграції потрібно виконати **в SQL Editor існуючого Supabase-проєкту**.

## Порядок розгортання

1. Запустіть [vatra-community-settings-rls.sql](vatra-community-settings-rls.sql).
   Цей захищений тригер забороняє створювати нові групові дописи звичайним учасникам **навіть при старих RLS-політиках**. Творець/адміністратор може публікувати від спільноти чи від себе, модератор (якщо `moderatorsCanPost` не вимкнуто) — тільки від себе. Також тригер забороняє нові коментарі в спільноті з вимкненими коментарями.
2. Запустіть [vatra-community-gallery.sql](vatra-community-gallery.sql).
   Додає RLS на записи `groupMedia/<groupId>/<mediaId>` у наявній таблиці `app_data`: перегляд відповідно до типу групи, завантаження тільки творцем/адміном/дозволеним модератором, видалення власником запису або адміном/творцем.
3. Якщо використовуєте відкладені дописи — повторно застосуйте [vatra-scheduled-posts.sql](vatra-scheduled-posts.sql), щоб планувальник перевіряв нові права ролей перед публікацією.
4. Основний файл [app-data-schema.sql](app-data-schema.sql) теж оновлений для **нових установок**. Для чинної бази достатньо цільових міграцій вище; без потреби не запускайте усі історичні міграції повторно.

## Як це працює

- Звичайний учасник бачить дописи та може коментувати, якщо коментарі дозволені, але не може публікувати.
- На сторінці спільноти показуються шість останніх учасників; нові приєднання отримують `joinedAt`. Для старих записів `true` точного часу немає; порядок таких записів не можна визначити достовірно.
- У редакторі поста питання «Додати медіа в галерею?» з’являється лише за наявності фото/відео. Вибір записується в `addMediaToGallery`. Історичні пости без цього поля зберігають колишню видимість.
- Під час створення спільноти можна вибрати `galleryAutoInclude`. Це значення — лише початковий стан перемикача при кожному дописі, його можна змінити.
- Групові альбоми описуються в `groups/<id>.photoAlbums`, а окремо завантажені файли — в `groupMedia`. Фото та відео з дописів **не копіюються** повторно в Storage.
- Усі завантажені фото/відео зберігаються в наявному Supabase Storage `vatra-media`. Видалення запису з галереї прибирає його з переліку, але **не видаляє** сам файл зі Storage; це запобігає випадковому видаленню файлу, який використовується в іншому дописі. Для повного очищення невикористаних файлів потрібна окрема серверна перевірка посилань.

## Перевірка на двох акаунтах

1. Акаунт A — творець спільноти. Акаунт B — звичайний учасник.
2. З акаунта B спробуйте знайти кнопку створення допису (її не має бути) і спробуйте прямий запит на створення `groupPosts` (має відхилитися у Supabase).
3. Призначте B модератором. Перевірте публікацію від себе та неможливість опублікувати від імені групи.
4. Вимкніть `moderatorsCanPost`, потім знову перевірте заборону. Перевірте вимкнення коментарів.
5. Увімкніть галерею: створіть допис із фото та відео, перевірте прапорець, переключіть його і перевірте відповідні вкладки «Фото», «Відео».
6. Створіть альбом, додайте фото окремо через вкладку «Фото», виберіть альбом, перевірте перегляд і видалення запису.
7. Перевірте коментарі з фото, відповіді, сортування, меню дій, модальне вікно учасників і адаптивність на вузькому екрані.

**Важливо:** GitHub-публікація й перевірка синтаксису не означають успішну перевірку міграцій на реальній базі. Не використовуйте `service_role` на клієнті; RLS має залишатися ввімкненим.
