# ВАТРА — останнє оновлення: техпідтримка, правила, псевдоніми та навігація

## Застосуйте міграції в Supabase SQL Editor

Це додаткові міграції до вже встановлених схем ВАТРИ. Спочатку мають бути застосовані `vatra-staff-verification.sql` та `vatra-support-desk.sql`.

1. **`vatra-support-alerts.sql`** — нові повідомлення в техпідтримку, сповіщення власнику, призначеному працівнику та користувачу, статус прочитання, оповіщення після перепризначення. Запускайте в SQL Editor один раз; виконання в транзакції.
2. **`vatra-staff-by-handle.sql`** — призначення, зміна й відкликання ролей та призначення звернень за поточним унікальним @псевдонімом. Сервер визначає UID один раз і зберігає призначення за UUID, тому зміна псевдоніма не забирає роль.

Не запускайте базовий `app-data-schema.sql` повторно на продуктивній базі без окремого резервного копіювання й перевірки RLS.

## Що змінилось у ВАТРІ

- Правила персоналу відкриваються на самому сайті як фірмове модальне вікно **«Повні правила персоналу ВАТРИ»** в розділі **Адмінпанель → Обов’язки**. Посилання на GitHub прибране.
- Біля **Техпідтримка ВАТРИ** в меню акаунта, налаштуваннях та адміністративній вкладці з'являється лічильник непрочитаних службових повідомлень. Також над дзвіночком і всередині випадаючих сповіщень є повідомлення, що відкриває відповідний діалог.
- Отримувачами є автор звернення, призначений оператор, власник; якщо оператора ще немає — доступні співробітники техпідтримки. Відправник не отримує оповіщення про власне повідомлення.
- Перегляд звернення позначає його сповіщення прочитаними тільки для поточного користувача. Оновлення лічильників працює під час відкритої ВАТРИ, приблизно кожні 8 секунд. Це не Web Push при закритій вкладці.
- В черзі звернень, повідомленнях і списку призначених працівників відображається ім’я, прізвище та @псевдонім із публічного профілю (коли він заповнений і доступний).
- Власник назначає працівників і призначає техпідтримку **за @псевдонімом**, а не вручну за UID. Сервісний статус закріплено за Auth UID.
- Замість вигаданого меню правої кнопки доступне стандартне меню браузера. Бічні розділи та посилання **«Усі фото»** й **«Переглянути всі»** є справжніми посиланнями, підтримують Ctrl+click, середню кнопку миші та «Відкрити у новій вкладці».
- Блок скарг отримав компактні фільтри, вирівняні поля, окремі картки й зрозумілі відомості про заявника.

## Тестування

1. Створіть два тестові акаунти (користувач і співробітник з роллю `support`) та переконайтесь, що власник налаштований.
2. Користувач відкриває звернення. Перевірте новий лічильник у співробітника й власника без перезавантаження після 8 секунд.
3. Співробітник відповідає. Перевірте сповіщення користувачу й те, що відкриття діалогу прибирає його непрочитаний індикатор.
4. Призначте роль за `@псевдонімом`, потім змініть псевдонім у тестового працівника: роль повинна зберегтися. Зніміть за його новим псевдонімом.
5. У браузері перевірте стандартне контекстне меню на посиланнях розділів та відкриття «Усі фото» в новій вкладці.
6. Перевірте модальне вікно правил в адмінпанелі та вигляд скарг на вузькому екрані.

Зміни у GitHub **не означають застосування SQL у Supabase**. Повноцінне тестування RLS, браузерних сповіщень і посилань у живому середовищі необхідне.
