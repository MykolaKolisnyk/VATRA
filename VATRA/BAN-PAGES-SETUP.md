# ВАТРА — сторінки блокувань і стабільність адмінпанелі (31.10.2026)

## Нова обов’язкова міграція

Після встановлення `vatra-moderation-center.sql`, `vatra-staff-verification.sql` і `vatra-support-desk.sql` виконайте через **Supabase → SQL Editor**:

**`VATRA/vatra-ban-public-pages.sql`**

Вона змінює сувору політику читання `app_data`: публічні профілі й метадані спільнот більше не приховуються через бан. Контент та дії заблокованих залишаються обмеженими попередніми RLS-політиками. Зверніть увагу: це **не** відключає вхід у Supabase Auth.

## Сторінка заблокованого користувача

- Профіль не зникає зі списків друзів або пошуку. При вході на його адресу `#/profile/UID` ВАТРА показує екран блокування замість звичайної сторінки.
- Інші відвідувачі бачать факт блокування.
- Сам власник акаунта бачить причину, дату рішення і термін (безстроковий або до певної дати), якщо вони є у базі.
- Для звернення/оскарження доступна техпідтримка; прямі спроби публікацій відхиляє серверна політика.

## Сторінка заблокованої спільноти

- Назва й ID спільноти залишаються в публічних списках і результатах пошуку.
- При відкритті `#/community/ID` відображається сторінка «Цю спільноту заблоковано ВАТРОЮ».
- Лише творець спільноти бачить причину та строк через публічний статусний API. Сторонні бачать лише статус; службові дані уповноважені працівники отримують через окрему адмінпанель.

## Адмінпанель

- При виході з адмінпанелі активна вкладка скидається на «Скарги».
- Старі значення форми блокування не залишаються як заповнений чернетковий текст.
- У списку блокувань відображаються ім’я, прізвище та псевдонім за даними `publicProfiles`, поряд із незмінним UID. Для спільнот показується назва та ID.
- В журналі біля UID виконавця та цілі дії підтягуються імена, якщо профіль доступний.
- Якщо інший компонент помилково перемалював вміст, але адреса ще `#/admin`, панель відновлюється автоматично.

## Перевірки перед запуском

1. Застосуйте новий SQL у живій базі **після** попередніх міграцій. Без цього нова сторінка блокування не зможе дістати статус.
2. Заблокуйте тестовий акаунт із причиною та строком. Перевірте його на іншому акаунті й на власному. Переконайтесь, що він не зник із друзів та пошуку.
3. Заблокуйте тестову спільноту. Перевірте її назву в списку й окремий екран блокування.
4. Перевірте через Supabase REST з тестовим токеном: заблокований користувач не повинен створювати дописи чи змінювати заборонені дані.
5. Поверніть тестовому акаунту і спільноті доступ і перевірте звичайні сторінки.
6. В адмінпанелі відкрийте «Користувачі» → введіть текст, вийдіть у налаштування, знову увійдіть. Має відкритися «Скарги», без старого чернеткового введення.
7. Відкрийте своє фото профілю, закрийте його й перевірте, що меню зміни фото не залишилося видимим.

**Увага:** код у GitHub не означає, що міграцію вже застосовано в Supabase. Повний браузерний тест на тестових акаунтах після міграції необхідний.

## Оновлення 31.10.2026: видалені сторінки, приватні деталі, запуск

- Сторінка має виглядати як профіль без дописів: зверху ім’я й позначка статусу, нижче повідомлення ВАТРИ.
- Для публічних відвідувачів **ніяких** дат, причин і строків адміністративного блокування. Ці відомості доступні лише **самому заблокованому акаунту** (або творцю заблокованої спільноти). Це перевіряє серверний RPC, а не лише приховує HTML.
- Список друзів і пошук лишають профіль, але замість його аватара показується SVG блокування. Відкриття заблокованого профілю спершу перевіряє стан на сервері й не показує його звичайну сторінку під час перевірки.
- Для **запланованого** видалення або остаточно **видаленого** акаунта RPC повертає стан `deleted`; інша SVG-іконка показується в списках, де запис профілю ще доступний.
- Для видалених назавжди акаунтів лишається лише запис статусу (`vatra_account_tombstones`, UID + час). Він не містить фото, імені чи приватних полів; після повного видалення таку людину не можна продовжувати показувати в пошуку за ім’ям.

### Сервер: що застосувати власнику проєкту

1. Переконайтесь, що в потрібному проєкті виконано базові міграції `vatra-moderation-center.sql`, `vatra-staff-verification.sql`, `vatra-support-desk.sql`.
2. Виконайте **`VATRA/vatra-account-lifecycle.sql`**, щоб створити таблицю життєвого циклу, статусні записи та оновити функцію очищення.
3. Виконайте **`VATRA/vatra-ban-public-pages.sql`**, щоб оновити RLS і RPC `vatra_public_ban_status`.
4. Перевірте результат в іншому акаунті: RPC має повернути `canSeeDetails: false`, а `reason`, `expiresAt`, `sinceAt` — `null`. Власник заблокованого акаунта має отримувати свій статус з `canSeeDetails: true`.
5. Не запускайте повне видалення живих акаунтів як тест. Процедура фонового очищення потребує **окремо розгорнутих Edge Function та cron** (див. `ACCOUNT-LIFECYCLE-DEPLOY.md`); сама SQL-міграція цього не робить.

### Діагностика, якщо ВАТРА не стартує

- На головній сторінці має з’явитися завантажувальний екран. Після старту він автоматично зникає.
- **E01**: основний JS-модуль або залежність не завантажилися. Перевірте вкладки Console та Network у DevTools (F12). Для бібліотеки Supabase передбачено резервний CDN.
- **E02**: модуль почав роботу, але запуск зупинився. Перегляньте першу червону помилку в Console і файл, на який вона вказує.
- Після публікації коміту зробіть **Ctrl+Shift+R** для оновлення ресурсів без старого кешу.
- Тести за самими файлами GitHub не підтверджують, що GitHub Pages і Supabase доступні саме з браузера користувача.
