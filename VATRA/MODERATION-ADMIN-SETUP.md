# Адмінпанель ВАТРИ — встановлення та використання

> **Оновлення 31.10.2026:** Для розподілу посад, заявок на верифікацію та галочок спільнот обов’язково застосуйте також `VATRA/vatra-staff-verification.sql` і вручну призначте власника в `vatra_network_owners`. Повна нова інструкція: [`STAFF-VERIFICATION-SETUP.md`](./STAFF-VERIFICATION-SETUP.md). Попередній механізм `vatra_verification_admins` більше не визначає ролі в новій адмінпанелі.


## Підготовка

Перед запуском переконайтеся, що застосовані, **у такому порядку**:

1. `VATRA/app-data-schema.sql`
2. `VATRA/vatra-unique-handles-verification.sql`
3. **`VATRA/vatra-moderation-center.sql`** — новий модуль модерації.

Виконувати у **Supabase → SQL Editor** із правами власника бази. Третій файл містить SQL-транзакцію (`begin; … commit;`) та не видаляє наявні скарги/блокування. Повторний запуск підтримується.

> Якщо ви пізніше перевиконуєте базовий `app-data-schema.sql`, він може пересоздати RLS-політики на `app_data`. Тоді **повторно виконайте міграції №2 та №3**, щоб не втратити перевірки прав і обмеження.

### Власний ID адміністратора

Із Supabase **Authentication → Users** скопіюйте ваш **User UID** (UUID). Надайте тільки собі права:

```sql
insert into public.vatra_verification_admins(user_id)
values ('ЗАМІНІТЬ_НА_ВАШ_UUID')
on conflict do nothing;
```

Це єдиний дозволений шлях первинного призначення адміністратора. Не відкривайте таблицю `vatra_verification_admins` для звичайних користувачів і не вставляйте на клієнт `service_role` ключ.

## Де знаходиться

**ВАТРА → Налаштування → Адмінпанель ВАТРИ** (кнопка в лівій навігації налаштувань, бачить лише авторизований адміністратор).

- **Скарги:** окрема черга, фільтр статусу, пошук, дати, швидке відкриття матеріалу, відправлення відповіді та зміна статусу: нова / розглядається / вирішена / відхилена. Натискайте «Завантажити ще 300 скарг» для старіших звернень.
- **Користувачі:** бан/розбан за `@псевдонімом` **або UID**. Підтримуються 24 години, 3 дні, 7 днів, 30 днів або безстроково.
- **Спільноти:** бан/розбан за ID спільноти, із тимчасовими строками.
- **Контент:** приховати/відновити допис, коментар або відео за точним шляхом в `app_data`.
- **Верифікація:** видача/відкликання синьої галочки за `@псевдонімом`; галочка прив’язана до UID, тому не зникає після перейменування.
- **Журнал:** дії адміністраторів із датами, причинами та цільовими ID.

Нові скарги показуються в адмінпанелі; лічильник відкритих скарг перевіряється біля іконки сповіщень приблизно кожні 90 секунд, **поки сайт відкрито**.

Користувачі мають у налаштуваннях вкладку **«Мої скарги»** для відстеження статусу й читання відповіді. Раніше подані скарги імпортуються з `app_data` під час встановлення SQL. Нові — додаються серверним тригером.

## Права і обмеження

- Усі ризикові адміністративні команди проходять через **Supabase SECURITY DEFINER RPC** та перевірку адміністратора на сервері. Сайт не дає можливості самопризначення прав.
- Бан акаунта **обмежує публікації та взаємодії на рівні `app_data`** і ховає його дописи в основних запитах, але **не відключає вхід у Supabase Auth**. Для повного блокування входу необхідна окрема серверна інтеграція Supabase Auth Admin API, яку не можна викликати із браузера звичайним ключем.
- Заблоковані спільноти та приховані матеріали відсікаються політиками читання для авторизованих і гостьових запитів до `app_data`; матеріали не видаляються назавжди.
- У панелі немає доступу до приватних зашифрованих повідомлень користувачів. Надання такого доступу не є частиною модерації.

## Перевірка після міграції

1. Увійдіть як адміністратор і відкрийте адмінпанель.
2. У другому тестовому акаунті надішліть скаргу. У першому відкрийте «Скарги», дайте відповідь і закрийте звернення.
3. Перевірте, що другий акаунт читає відповідь у «Мої скарги».
4. Заблокуйте **тестовий** акаунт на 24 години та переконайтеся, що новий допис не створюється.
5. Зніміть бан, повторіть публікацію, перевірте журнал.
6. Окремо перевірте бан/розбан **тестової** спільноти та приховування/відновлення допису.
7. Звичайний користувач не повинен бачити адмінпанель або виконувати RPC-команди модерації.

**Код у GitHub не означає, що SQL уже встановлений у живу базу.** Після виконання SQL і публікації сайту потрібне тестування на реальних тестових акаунтах.
