# ВАТРА — видалення акаунта та неактивність (обов’язкове серверне налаштування)

Код клієнта вже містить розділ **Налаштування → Акаунт і видалення**.
Він **не може видаляти користувачів напряму з браузера**: для цього потрібні
Supabase Edge Function, SQL-міграція і регулярний серверний запуск.

## Розгортання власником Supabase

1. У **Supabase → SQL Editor** запустити
   [vatra-account-lifecycle.sql](vatra-account-lifecycle.sql).
   Він створює таблицю `vatra_account_lifecycle` із RLS і серверну процедуру
   `vatra_purge_user_data`. Не вимикайте RLS.
2. У Supabase CLI / проєкті, якому належить цей URL, встановити секрет:
   `supabase secrets set VATRA_LIFECYCLE_CRON_SECRET=<довгий-випадковий-секрет>`.
   Уникайте пробілів; використовуйте секрет щонайменше з 32 випадкових байтів.
   **Не додавайте його до GitHub або браузерних JavaScript-файлів.**
3. Із кореня репозиторію під’єднайте CLI до правильного Supabase-проєкту:
   `supabase link --project-ref rjasunoawrxvetwadylh`.
   Розгорніть функцію:
   `supabase functions deploy vatra-account-lifecycle --no-verify-jwt`.
   JWT не перевіряється на рівні шлюзу, бо щоденне завдання викликає функцію
   без JWT, але сама функція **обов’язково перевіряє** токен користувача через
   `auth.getUser()`; завдання — через окремий секрет.
4. У **Database → Extensions** увімкніть `pg_cron` і `pg_net`.
   У **Vault** створіть секрет з назвою `vatra_lifecycle_cron_secret` і
   **тим самим значенням**, що у `VATRA_LIFECYCLE_CRON_SECRET`.
   Після цього запустіть SQL, наведений нижче.
5. Перевірте, що виклик функції `status` у розділі акаунта показує статус,
   а не помилку `Функція видалення акаунта ще не активована`. Перевірте
   запит/скасування на **окремому тестовому акаунті**, який не володіє спільнотою.

## SQL: щоденний серверний запуск

```sql
select cron.schedule(
 'vatra-account-lifecycle-daily',
 '15 3 * * *',
 $cron$
 select net.http_post(
   url := 'https://rjasunoawrxvetwadylh.supabase.co/functions/v1/vatra-account-lifecycle',
   headers := jsonb_build_object(
     'Content-Type','application/json',
     'x-vatra-cron-secret',
      (select decrypted_secret from vault.decrypted_secrets
       where name = 'vatra_lifecycle_cron_secret')
   ),
   body := '{"action":"sweep"}'::jsonb,
   timeout_milliseconds := 120000
 ) as request_id
 $cron$
);
```

Перевірте виконання через **Supabase Cron → History** і журнали Edge Functions.
Невдале видалення не треба приховувати: воно має залишатися для повторного
серверного запуску/обробки адміністратором. Через щоденний розклад остаточне
видалення відбувається **після** завершення 30-денного строку, на наступному
успішному проході cron, а не рівно до секунди.

## Поведінка

- Ручне видалення вимагає введення слова **ВИДАЛИТИ**, не видаляє нічого
  миттєво, створює заявку на 30 днів. До завершення строку її можна скасувати
  через **Акаунт і видалення** після входу в акаунт.
- Автовидалення вимкнене за замовчуванням. Вибір 7/30/365 днів рахується
  за серверно зафіксованими відвідуваннями. Коли поріг неактивності минув,
  щоденний запуск створює **додатковий 30-денний** строк для відновлення.
- Всі критичні дії виконуються сервером. Браузер не отримує `service_role`.
- Акаунт власника спільноти не можна остаточно видалити без передачі
  власності/видалення спільноти, щоб не знищити сторонні дані.
- Сервер видаляє особисті записи `app_data`, контент, взаємодії, медіафайли з
  `vatra-media/<uid>/...` та Auth-запис. Це **незворотна дія**.
- Додаткові зовнішні системи, резервні копії, аудит та сторонні інтеграції,
  якщо вони є, треба оцінити окремо: у цій функції немає доступу до таких
  систем. Не обіцяйте видалення з усіх резервних копій негайно.
- Ніколи не запускайте очищення просто у браузері або на основі даних,
  наданих користувачем без перевірки Supabase Auth.

**Не вважайте функцію робочою, доки не розгорнуті SQL, Edge Function,
cron і не проведено тест у живому Supabase.** Файли GitHub самі по собі
не змінюють Supabase.
