# Наскрізне шифрування повідомлень VATRA — v1 (beta)

## Що реалізовано

Для **особистих чатів 1:1** нові повідомлення шифруються у браузері до відправлення у Supabase.
На сервер передається тільки `encrypted`: шифротекст, IV, версія алгоритму,
ідентифікатори ключів і криптографічний підпис. Поле `text` для нових повідомлень
не створюється. У списках чатів використовується текст «🔒 Зашифроване повідомлення».

- Web Crypto API: ECDH P-256 для спільного секрету, HKDF-SHA-256 для ключа,
  AES-256-GCM для конфіденційності та цілісності.
- Окремий ECDSA P-256 ключ кожного користувача підписує шифротекст і метадані
  відправника. Підпис перевіряється перед розшифруванням.
- Неекспортовані приватні `CryptoKey` зберігаються **лише у IndexedDB браузера**.
  У Supabase (`e2eeKeys/<uid>`) публікуються тільки два відкриті ключі.
- Відбитки ключів прив’язуються до співрозмовника на цьому пристрої за моделлю
  TOFU (trust on first use). Після підміни ключа надсилання блокується.
- Коди безпеки показані в чаті. Для підтвердження особи їх **обов’язково**
  слід звірити з учасником іншим надійним каналом.
- Коли ключів ще немає, приватний ключ втрачений, підміна ключа виявлена або
  база не має відповідних правил RLS, нові повідомлення **не надсилаються
  відкритим текстом**.

## Налаштування Supabase

Оновити SQL із `VATRA/app-data-schema.sql` у **тому самому Supabase-проєкті**
через SQL Editor. Оновлені правила дають читання відкритих E2EE-ключів
авторизованим користувачам і дозволяють змінювати відкритий ключ тільки його власнику.
**Не вимикайте RLS**. SQL також встановлює тригер `vatra_require_encrypted_messages`: він не дозволяє записувати нові приватні повідомлення у відкритому тексті, забороняє змінювати чужі повідомлення та захищає від альтернативних шляхів збереження незашифрованого тексту. Перезапис приватних ключів у таблицю заборонений.

Після застосування SQL оновити сторінку через Ctrl+F5 і повторно увійти в обидва акаунти.
Вони повинні створити відкриті ключі на своїх пристроях, після чого відкрити чат.

## Обмеження та попередження

Це **не протокол Signal** і не продукт, що пройшов незалежний криптографічний аудит.

1. Поки немає Double Ratchet / попередньо опублікованих одноразових ключів:
   **немає forward secrecy чи post-compromise security**.
2. **Немає синхронізації між пристроями чи резервного відновлення ключів**.
   Якщо користувач очистить дані сайту або перейде на інший пристрій, старі
   повідомлення можуть назавжди стати недоступними. Поточна версія **блокує**
   автоматичне створення іншого приватного ключа для вже зареєстрованого акаунта,
   щоб не створювати хибне відчуття захисту.
3. При першому контакті сервер, що підмінює відкритий ключ, може бути атакувальником.
   **Потрібна звірка відбитків ключів поза ВАТРОЮ**. TOFU захищає лише від подальшої
   непомітної зміни ключа.
4. Історичні повідомлення, які вже були збережені як `text`, **не стають
   зашифрованими заднім числом**. Інтерфейс прямо позначає їх як старі незахищені.
5. Метадані (учасники, час, розмір повідомлення), списки чатів і реакції **не
   шифруються**, так само як публічні фото, відео та пости. Групові чати
   не підтримуються цим модулем.
6. Код сайту із GitHub Pages і зовнішні JavaScript-залежності потрібно вважати
   довіреною частиною клієнта. Компрометація завантаженого JS, XSS або пристрою
   може розкрити текст. Перед виробничим використанням потрібні аудит,
   захист від XSS, перевірка залежностей, CSP та окрема політика резервного
   копіювання й ротації ключів.
7. Стан «Онлайн» не пов’язаний із фактом готовності E2EE. Якщо ключів немає,
   у чаті показується точна помилка, і надсилання недоступне.

## Перевірка

Запустити `node --test VATRA/tests/e2ee.test.mjs` (Node.js 22+).
Тести перевіряють шифрування/розшифрування у двох напрямках,
перевірку підписів, відмову від plaintext fallback, зміну ключів,
відсутність локального приватного ключа й унікальний IV.

GitHub Actions запускає той самий тест у
`.github/workflows/e2ee.yml`.

Додатковий ручний тест у **двох різних авторизованих браузерах/акаунтах**
із реальною базою Supabase обов’язковий. Він поки не виконаний автоматично.

## Вигляд інтерфейсу

Окремий `responsive.css`, що завантажується останнім, відповідає за адаптивні розміри і VK-подібну структуру профілю зі стилістикою ВАТРИ. Пропорції та відсутність горизонтального переповнення перевіряються браузерними тестами з реальним емулятором viewport в Chrome на ширинах 390, 768, 1024 та 1366 px (`VATRA/tests/layout.test.mjs`).
