# VATRA: завантаження функцій за потреби (2026-11-22)

## Контракт сторінок

`profile.html` і `feed.html` містять основні для маршруту JS/CSS та невеликий
`assets/js/feature-loader.js`. На старті **не** завантажують редактор історій,
додатковий інтерфейс редактора публікації або його стилі. Профіль також не
завантажує код/стилі альбомів, доки користувач не відкриє вкладку.

- `story` → `story-editor.css` → `story-editor.js`, після кнопки «Створити історію»
- `composer` → `post-composer.css` → `post-composer-ui.js`, після відкриття редактора допису
- `albums` → `photo-albums.css` → `photo-albums.js`, після вкладки «Фотографії»
- `profile-gallery` → `profile-gallery.js` (без окремого CSS), лише після
  переходу до вкладок «Фотографії», «Відео» або «Кліпи»
- `avatar-editor` → `profile-avatar-editor.js` (без окремого CSS), лише після
  вибору нового зображення аватара. Перегляд фото, коментарі, лайки,
  видалення/відновлення й обмеження доступу залишаються в основному профілі.
- `cover-viewer` → `profile-cover-viewer.js` (без окремого CSS), лише після
  відкриття поточної обкладинки. Профіль продовжує відображати мініатюру
  без окремого переглядача; анімація, оригінал і кнопка закриття всередині модуля.
- `cover-editor` → `profile-cover-editor.js` (без окремого CSS), після вибору
  файлу нової обкладинки профілю. Перегляд наявної обкладинки не залежить
  від цього модуля, оскільки потрібний лише власнику для кадрування.
- `gift` → `gifts.css` → `gift-viewer.js`, лише після натискання на подарунок.
  Каталог `gift-catalog.js` залишається на початковому маршруті; на `gifts.html`
  CSS вже підключений для карток і не запитується вдруге
- Запит `?album=<uuid>&photo=<uuid>` на профілі одразу підключає альбоми, з
  перевіркою доступу у Supabase RLS, без копіювання приватних даних у кеш.

Спільний завантажувач підтримує функції без окремого CSS та запам'ятовує Promise для кожної функції, щоб дві
одночасні дії не завантажували однаковий JS/CSS вдруге; чекає на готовність
CSS перед запуском JS; після мережевої помилки дозволяє повторити дію.
Додавання нової функції до loader не означає її автоматичне завантаження.

## Межі поточної оптимізації

- Повноекранний переглядач подарунків і галерею профілю винесено в окремі
  модулі. Початковий профіль зберігає лише компактний каталог подарунків та
  обробники відкриття медіавкладок; перевірка доступу `locked` залишається
  в основному коді до ініціалізації галереї.
- Повноекранний переглядач обкладинки відокремлено від аватара й
  початкового `profile.js`. Перший клік завантажує окремий модуль і
  запускає ту саму анімацію обкладинки; повторний клік використовує
  готовий модуль, а приватність перевіряє основний профіль.
- Редактор аватара відокремлено від початкового `profile.js`.
  Перший вибір файлу ініціалізує модуль один раз; при наступних відкриттях
  він повторно використовується. Під час завантаження одного редактора
  інший не відкривається; правила завантаження 30 МБ, публікації
  допису/історії за бажанням користувача та історія фото не змінені.
- Редактор обкладинки відокремлено від початкового `profile.js`.
  Вибір зображення викликає спільний завантажувач, після чого редактор
  ініціалізується один раз; статуси зайнятості запобігають одночасному
  кадруванню аватара й обкладинки. Обрізання та збереження не змінені.
- `post-media.js`, `post-interactions.js` та `profile.js` поки залишені
  як залежності основних сторінок. Подальше дроблення можливе після
  аудиту ініціалізації, підписок і підписаних медіапосилань.
- Основні CSS сторінки залишаються в HTML, щоб не спричинити стрибки
  верстки (FOUC). CSS модальних редакторів підключається **до** їх відкриття.
- При зміні fingerprints оновлювати шляхи у `feature-loader.js` та його
  `?rev=` в HTML, щоб уникати застарілих файлів у кеші браузера.

Тести: `feature-loader-smoke.mjs`, `photo-albums-smoke.mjs`,
`media-viewer-layout-smoke.mjs`, аудит `check-layout.mjs` та Playwright у GitHub Actions. Жодних змін Supabase,
Redis Secrets, даних користувачів або RLS для цієї оптимізації не потрібно.
